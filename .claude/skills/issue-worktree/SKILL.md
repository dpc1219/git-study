# issue-worktree: 요청 → 이슈 → 라벨 → 워크트리

새 작업을 "이슈 번호가 있는 전용 브랜치/워크트리"에서 시작하게 만든다. 이슈가 작업 기록이 되고, 워크트리 덕분에 다른 작업 중인 변경과 섞이지 않는다.
이 스킬은 **확인 없이 자동으로** 진행한다(사용자가 그렇게 정함). 대신 아래 안전 규칙을 반드시 지킨다.

참고 문서: 라벨 표·분류 규칙 `references/labels.md`, 본문 형식 `references/issue-template.md`.

## 절차

1. **요청 분석**: 요청에서 유형(기능/버그/문서/개선/리팩터링/질문), 주제(0~2개), 제목, 영문 slug를 정한다.
   - 정보가 부족해도 묻지 않고 합리적으로 채운다. 추정한 내용은 본문에 "(추정)"으로 표시한다.
   - slug는 영문 소문자-하이픈, 2~4단어 (예: `transfer-ratio`).
2. **본문 작성**: `references/issue-template.md` 형식으로 임시 파일(scratchpad)에 쓴다. 한국어, 체크리스트 포함.
3. **실행**:
   ```bash
   python .claude/skills/issue-worktree/scripts/start_issue.py \
     --title "[기능] 정류장별 환승 비율 분석 추가" --body-file <본문파일> \
     --type 기능 --topics "정류장·OD" --slug transfer-ratio
   ```
   스크립트가 하는 일: `gh` 로그인 확인 → 부족한 한글 라벨 생성 → 같은 제목의 열린 이슈 확인(있으면 재사용) → 이슈 생성 + 라벨(`유형, 주제…, 상태:진행중`) → `../<저장소>-worktrees/<번호>-<slug>`에 워크트리, `<접두사>/<번호>-<slug>` 브랜치 생성(기준 `main`).
   마지막 줄의 JSON에서 이슈 URL, 브랜치, 워크트리 경로를 읽는다.
4. **보고**: 이슈 URL, 라벨, 브랜치, 워크트리 경로를 짧게 알린다.
5. **작업 시작**: 이후 파일 수정·실행은 **그 워크트리 경로**에서 한다(`EnterWorktree` 도구가 있으면 그 경로로 진입, 없으면 절대 경로로 작업). 메인 작업 트리의 미커밋 변경은 건드리지 않는다.

## 작업 중·후

- 커밋은 `data-commit` 스킬 규칙을 따르고, 마지막 커밋 또는 PR 본문에 `Closes #<번호>`를 넣는다.
- PR을 열면 상태 라벨 교체: `gh issue edit <번호> --remove-label "상태:진행중" --add-label "상태:리뷰중"`. 병합 후 `상태:완료`.
- push·PR 생성은 사용자가 요청할 때만 한다.

## 안전 규칙 (자동 실행이라 필수)

- 공개 저장소일 수 있다. 요청문에 개인정보(카드번호·이름·연락처), 키·토큰, 원본 이동 이력 값이 있으면 **이슈에 옮기지 말고** 일반화한다.
- 대상은 `origin` 저장소뿐이다. `gh` 미로그인이거나 origin이 GitHub가 아니면 중단하고 알린다.
- 같은 제목의 열린 이슈가 있으면 새로 만들지 않는다(스크립트가 재사용). 유사하지만 제목이 다른 이슈가 의심되면 `gh issue list --search`로 먼저 확인한다.
- 기존 라벨의 색·설명을 덮어쓰지 않고, 이슈·라벨을 삭제하거나 이슈를 닫지 않는다.
- 이미 있는 브랜치/워크트리는 덮어쓰지 않고 재사용한다.
- 새 주제 라벨이 필요해 보여도 임의로 만들지 말고 주제 없이 진행한 뒤 사용자에게 제안한다.
