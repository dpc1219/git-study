# 데이터 분석 조직 커밋 컨벤션

기반: [Conventional Commits 1.0.0](https://www.conventionalcommits.org/ko/v1.0.0/)의 `type(scope): subject` 구조.
분석 조직에서는 "기능/버그"보다 **데이터·산출물·검증**의 변경이 많아 타입을 이에 맞게 확장했다.
데이터 버전관리 관행(코드와 데이터 변경을 구분해 기록, 변경 이유와 데이터 기준을 메시지에 남김)도 반영했다.

## 목차
1. 형식
2. 타입
3. 스코프
4. 제목·본문 작성 규칙
5. 파일 유형별 분류 기준
6. 예시
7. 하지 말 것

## 1. 형식

```
<type>(<scope>) : <제목>

<본문: 선택>

<꼬리말: 선택>
```

- 이 저장소의 기존 이력은 `feat : 시간대별 수요 패턴 분석 코드 추가`처럼 **타입 뒤에 공백 + 콜론 + 공백**을 쓴다. `git log`로 확인해 기존 형식이 있으면 그것을 따른다. 이력이 없으면 `type(scope): 제목`(공백 없는 콜론)을 쓴다.
- 스코프는 생략 가능하다. 쓰면 `type(scope)` 형태로 타입 바로 뒤에 붙인다.
- 제목은 한국어, 명사형 종결(`~ 추가`, `~ 수정`, `~ 생성`), 마침표 없음, 50자 안팎.
- 타입은 영문 소문자 고정(도구·검색 호환).

## 2. 타입

| 타입 | 쓰는 때 | 예 |
| --- | --- | --- |
| `feat` | 새 분석 코드·지표·모델·집계 로직 추가 | 시간대별 수요 분석 코드 추가 |
| `fix` | 집계·필터·조인 오류, 잘못된 결과를 내던 로직 수정 | 환승 중복 집계 오류 수정 |
| `data` | 원천/더미/마스터/매핑 데이터의 추가·갱신·삭제 | 노선 마스터 2026-10 갱신 |
| `result` | 분석 산출물(csv, xlsx 결과표, 그래프 이미지, 리포트 수치)의 생성·재생성 | 노선별 운영 성과 결과표 생성 |
| `qa` | 데이터 품질 검증·정합성 체크·이상치 규칙 | 하차 미태그 비율 검증 규칙 추가 |
| `viz` | 시각화·대시보드 코드나 스타일 | OD 히트맵 색상 팔레트 변경 |
| `refactor` | 결과는 같고 구조만 개선(함수 분리, 이름 변경) | 전처리 함수를 공통 모듈로 분리 |
| `perf` | 결과는 같고 실행 속도·메모리 개선 | 승하차 조인을 벡터화해 속도 개선 |
| `docs` | README, 데이터 사전, 분석 정의서, 주석 | 컬럼 정의서 추가 |
| `test` | 테스트·검증 스크립트 | 보정 로직 단위 테스트 추가 |
| `env` | 의존성, 가상환경, 설정, 경로 | requirements에 scipy 추가 |
| `chore` | 위에 안 맞는 잡무(.gitignore, 파일 이동) | .gitignore에 캐시 폴더 추가 |
| `revert` | 이전 커밋 되돌림 | 되돌림: 환승 보정 로직 변경 |
| `merge` | 브랜치 병합 커밋(기존 이력 관례) | 정류장 및 OD 분석 브랜치 병합 |
| `init` | 저장소·프로젝트 최초 구성 | 저장소 초기화 |

타입 고르는 팁
- 결과 숫자가 **달라지면** `feat`/`fix`, **같으면** `refactor`/`perf`.
- 코드 변경으로 산출물이 재생성됐어도 코드와 산출물은 별도 커밋(`feat`+`result`)이 원칙.
- 원본을 가공한 파일이 코드 입력으로 쓰이면 `data`, 코드 실행 결과로 나온 것이면 `result`.

## 3. 스코프

스코프는 **분석 주제 또는 파이프라인 단계**를 짧게 쓴다. 영문 소문자·snake_case 권장.

- 분석 주제: 스크립트/산출물 폴더 이름을 그대로 쓴다. (`time_demand`, `route_performance`, `stop_od`, `quality_user`)
- 파이프라인 단계: `ingest`(수집/적재), `clean`(정제), `feature`(파생변수), `model`, `report`.
- 여러 주제에 걸치면 스코프를 생략한다. 두 개 이상 나열하지 않는다(그럴 땐 커밋을 나눈다).

## 4. 제목·본문 작성 규칙

제목: 무엇을 했는지 한 줄. 파일명이 아니라 **분석 내용**을 쓴다.
- 좋음: `노선별 첨두시 회당 평균승객 산출 추가`
- 나쁨: `time_demand.py 수정`, `분석 코드 업데이트`

본문은 아래 중 하나라도 해당하면 쓴다(빈 줄 뒤, 한 줄 72자 안팎).
- **왜** 바꿨는지(오류 원인, 요청 배경, 정의 변경)
- **분석 기준**: 기간, 대상 범위, 필터 조건, 지표 정의(예: "첨두 = 07~09시, 18~20시")
- **결과 영향**: 수치가 얼마나 바뀌는지 (예: "노선 A 회당 승객 12.3 → 11.8")
- **데이터 출처/버전**: 사용 파일명, 갱신일, 건수
- 산출물 커밋이면 **어떤 코드/커밋에서 생성됐는지** (재현용)

꼬리말: 이슈·티켓 번호(`Refs: #12`), 파괴적 변경(`BREAKING CHANGE: ...` — 산출물 컬럼명·스키마가 바뀌어 후속 분석이 깨질 때).
스키마 변경은 제목에 `!`도 가능: `feat(stop_od)!: od_matrix 컬럼명 변경`.

## 5. 파일 유형별 분류 기준 (기본값)

| 경로·확장자 | 기본 타입 | 비고 |
| --- | --- | --- |
| `*.py`, `*.sql`, `*.R` 분석/집계 스크립트 | `feat` (신규) / `fix` / `refactor` | diff 보고 판단 |
| `*.ipynb` | `feat`/`fix`, 출력만 변경이면 `result` | 출력 제거 권장 |
| 원천·더미 데이터 `*.xlsx`, `*.csv`, `*.parquet` (입력 위치) | `data` | `generate_dummy_data.py` 같은 생성기는 `feat`/`data` 판단 |
| `output/`, `results/`, `reports/` 아래 파일 | `result` | 주제 폴더명 = 스코프 |
| `*.png`, `*.svg`, `*.html` 차트 | `result` (생성물) / `viz` (그리는 코드) | |
| `README*`, `docs/`, `*.md` | `docs` | |
| `requirements*.txt`, `environment.yml`, `pyproject.toml`, `*.cfg` | `env` | |
| `.gitignore`, `.gitattributes`, 설정류 | `chore` | |
| `test_*.py`, `tests/` | `test` | |

## 6. 예시

```
feat(time_demand) : 시간대별 수요 패턴 분석 코드 추가

노선유형·이용자구분별 시간대 이용건수/비중과 첨두시간 집중률 산출.
첨두 기준은 07~09시, 18~20시.
```

```
result(time_demand) : 시간대별 수요 분석 결과표 13종 생성

bus_alighting.xlsx(2026-09 기준 12,000건) 대상. time_demand.py 실행 결과.
```

```
fix(stop_od) : 환승 정류장 OD 중복 집계 수정

동일 카드의 30분 내 재탑승을 별도 통행으로 세던 문제 수정.
transfer_hubs 상위 10개 정류장 순위 일부 변경.
```

```
qa(quality_user) : 하차 미태그 비율 카이제곱 검정 추가
```

```
data : 노선·하차 더미 데이터(xlsx) 생성

generate_dummy_data.py 시드 42 고정, 노선 20개 / 승하차 12,000건.
```

## 7. 하지 말 것

- 한 커밋에 코드 + 산출물 + 문서를 섞기 (예외: 신규 스크립트와 그 첫 산출물이 작을 때)
- `수정`, `업데이트`, `fix bug`, `최종`, `final2` 같은 정보 없는 제목
- 개인정보가 담긴 원본 데이터·`.env`·토큰 커밋
- 재생성 가능한 대용량 파일을 매번 커밋하기 (필요하면 DVC/스토리지 + `.gitignore`)
- 결과 수치가 바뀌는 변경을 `refactor`로 숨기기
